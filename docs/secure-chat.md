# 房间聊天：威胁模型与防护边界

本文说明 `src/net/secureChat.ts`、`src/ui/chatPanel.ts` 和服务器 `rtc` 信令分支提供的安全属性、隐私边界与当前验收方式。

## 架构

- **文字传输**：两端通过 WebRTC `RTCDataChannel` 发送文字，传输层使用 DTLS 加密的 SCTP。
- **语音传输**：两端通过 WebRTC 音频轨道发送语音，媒体层使用 DTLS-SRTP 加密。
- **信令服务**：游戏服务器验证发送座位与目标座位，然后把 SDP 和 ICE 原样转发给同一房间内的在线玩家。
- **能力协商**：服务器在 `welcome.capabilities` 中声明 `chat-v1`。新客户端连接旧服务器时得到空能力集，游戏正常运行，聊天入口保持隐藏。
- **连接拓扑**：四名玩家最多建立六条两两直连；座位顺序较小的一方主动发起连接。
- **网络发现**：当前使用 Google 公共 STUN 服务完成 NAT 地址发现。

## 身份与密钥

- 每个标签页通过 `RTCPeerConnection.generateCertificate` 在内存中生成一张临时 ECDSA P-256 证书。
- 浏览器在 DTLS 握手中验证证书，并将证书指纹写入协商 SDP。
- 双方安全码由规范化后的两个 DTLS 指纹计算 SHA-256，再取前 64 位并显示为 20 位数字。
- 安全码由规范化后的指纹集合计算，因此两端显示相同结果。
- 玩家刷新页面后生成新证书，安全码随之变化。
- 已验证队友的安全码发生变化时，界面撤销该 Peer 的已验证状态，暂停文字传输，并立即停止语音发送与播放。

## 信任边界

- **网络窃听者**：DataChannel 与语音轨道使用浏览器标准 WebRTC 加密，正文和媒体只在两端浏览器中解密。
- **被动服务器**：服务器可观察座位关系、时间、信令大小和 SDP/ICE 内容；聊天正文与语音保持在端到端加密链路内。
- **主动信令篡改**：服务器可以尝试替换 DTLS 指纹制造中间人；两端安全码会不同，人工核对可以发现。
- **聊天身份**：文字通过加密链路传输；玩家核对安全码后，链路身份得到本地确认。
- **语音身份**：语音采用更严格的本地策略，只有 `secure + safety code verified` 的 Peer 能获得发送轨道或播放远端音频。
- **验证变化**：安全码变化时，该 Peer 的文字与语音立即暂停；重新核对后恢复文字，并由玩家主动开启语音。
- **本地记录**：聊天记录最多保留 100 条并仅保存在内存；离开房间、切换能力或关闭页面会清空记录和信任状态。
- **页面安全**：所有昵称和消息使用 `textContent` 渲染，消息长度、接收频率和发送频率均有上限。

## 媒体生命周期

- 麦克风使用单一 pending 请求：重复点击复用同一权限请求。
- `sessionGeneration` 标记当前房间会话；离开房间后返回的旧授权结果会立即停止全部轨道。
- `desiredMicOn` 表示玩家的目标状态；`micOn` 只在真实 MediaStream 已安装时成立。
- `micPending` 驱动界面显示“授权中…”，授权期间按钮保持禁用。
- 麦克风按钮只在当前用户存在已验证队友时启用；可信 Peer 数量降为零时，本地麦克风自动关闭。
- `voiceRevision + voiceQueue` 串行应用轨道切换，旧异步结果在新安全策略生效前失效。
- 每个 Peer 的 DataChannel、远端音频、ICE 队列和媒体轨道都随 Peer 关闭一起释放。

## 连接恢复

- PeerConnection 进入 `failed` 或 `closed` 后，主动方按 1 秒、2 秒、4 秒、8 秒、15 秒的间隔指数退避重连。
- 每个座位最多存在一个重试定时器，离开房间或连接恢复时立即取消。
- `disconnected` 状态持续 5 秒后进入失败重连。
- DataChannel 意外关闭会触发同一个重连状态机。
- 只有座位序号较小的一方主动重连，避免双方同时创建冲突连接。

## 元数据

- 游戏服务器可以看到谁与谁建立连接、连接时间、信令大小以及 SDP 中的 ICE 候选地址。
- STUN 服务和对方玩家可以看到公网 IP。
- 网络观察者可以推断消息长度和发送频率。
- 当前房间使用四字符公开邀请码，访问控制依赖邀请码分发。

## 需要额外防护的攻击者

- 恶意网页代码可以从页面运行时直接读取明文；签名桌面或移动客户端可以扩大防护边界。
- 被攻破的设备、浏览器扩展、屏幕录制和摄录设备可以接触明文。
- 接收方主动截图或转述内容。
- 文字聊天的身份保证依赖双方核对安全码；核对完成后，对端身份得到本地确认。
- 部分企业 NAT 或对称 NAT 组合需要 TURN 中继才能直连；当前 UI 会显示连接失败并保持重试。

## 自动化验收

`pnpm test` 覆盖安全码格式、顺序无关性、指纹变化和客户端协议校验。`pnpm test:server` 使用真实 WebSocket 服务覆盖能力声明、定向转发、`from` 注入、自转发和观战者消息丢弃、UTF-8 大小限制和非法消息。

`pnpm smoke` 使用两个真实 Chromium 上下文和模拟麦克风，覆盖双端 ICE、安全码一致、核对前语音禁用、核对后 RTP 双向字节增长、DataChannel 文本送达，以及一端刷新后安全码变化、发送轨道卸载、远端音频关闭和麦克风停止。

发布前人工验收聚焦真实设备与公网网络：使用两台终端和真实麦克风确认语音互通，在真实 NAT 环境检查 STUN 成功率与失败提示，并由独立人员完成安全审查。
